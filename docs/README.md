# 🎓 수강 신청 시스템 (Enrollment System)

## 📌 프로젝트 개요

수강 신청 시스템은 사용자가 강의를 조회하고 신청 및 관리할 수 있는 웹 서비스입니다.

동시 요청이 집중되는 수강 신청 환경을 가정하여 **Spring Security와 JWT 기반 인증/인가**, **Kafka 기반 비동기 처리**, **데이터베이스 수준의 동시성 제어**를 구현했습니다.

수강 신청 요청을 처리하는 과정에서 동시 요청 증가로 **데드락이 발생하는 문제**를 확인했습니다. 원인을 분석한 결과 기존의 조회 후 엔티티 수정 방식에서 동일한 강의 데이터에 대한 락 경쟁이 발생하고 있었고, 이를 해결하기 위해 **정원 확인과 신청 인원 증가를 하나의 조건부 UPDATE로 처리하도록 구조를 개선**했습니다.

JMeter로 1,000건의 동시 요청을 테스트한 결과 **데드락과 정원 초과 없이 데이터 정합성을 유지**하는 것을 검증했습니다.

---

## ✨ 주요 성과

* 조건부 UPDATE를 적용해 동시 요청 과정에서 발생한 데드락 해결
* 정원 확인과 신청 인원 증가를 원자적으로 처리하여 정원 초과 방지
* 복합 UNIQUE 제약조건을 적용해 동일 사용자의 중복 신청 방지
* Kafka Producer/Consumer 기반 비동기 수강 신청 처리 구조 구현
* JMeter를 활용한 1,000건 동시 요청 테스트로 데이터 정합성 검증

## 🏗️ 시스템 구조

### 수강 신청 처리 흐름

```text
사용자 요청
    ↓
Kafka Producer
    ↓
Topic (enrollment-request)
    ↓
Kafka Consumer Group
    ↓
조건부 UPDATE
(정원 확인 + 신청 인원 증가)
    ↓
수강 신청 정보 저장
```

수강 신청 요청은 Kafka Producer를 통해 Topic에 전달하고 Consumer Group에서 비동기로 처리하도록 구성했습니다.

Consumer에서는 데이터베이스의 조건부 UPDATE를 통해 **정원 확인과 신청 인원 증가를 하나의 연산으로 처리**한 후 수강 신청 정보를 저장합니다.

---

## 🗄️ 데이터베이스 설계
![수강 신청 시스템 ERD](./images/erd.png)

### 테이블 구성

* `Users`: 사용자 계정 및 권한 정보 관리
* `Classes`: 강의 정보, 정원 및 현재 신청 인원 관리
* `Enrollment`: 사용자와 강의 간 수강 신청 정보 관리

### 주요 관계

* 한 명의 강사는 여러 강의를 생성할 수 있습니다.
* 한 명의 사용자는 여러 강의를 신청할 수 있습니다.
* 하나의 강의에는 여러 사용자가 신청할 수 있습니다.
* `Enrollment` 테이블을 통해 사용자와 강의의 다대다 관계를 관리합니다.
* `(user_seq, class_seq)` 복합 UNIQUE 제약조건으로 동일 사용자의 중복 신청을 방지합니다.

## 🚀 동시성 문제 분석 및 개선

### 문제 상황

기존에는 수강 신청을 다음과 같은 방식으로 처리했습니다.

```text
강의 조회
    ↓
현재 신청 인원과 정원 비교
    ↓
엔티티의 신청 인원 증가
    ↓
수강 신청 정보 저장
```

동시 요청이 증가하면서 여러 트랜잭션이 동일한 강의 데이터를 조회하고 수정하게 되었고, 이 과정에서 락 경쟁이 발생했습니다.

특히 엔티티의 신청 인원을 변경하면 JPA의 변경 감지에 의해 UPDATE가 수행되기 때문에 여러 트랜잭션이 동시에 동일한 강의 데이터를 처리하는 상황에서 **데드락이 발생하고 일부 요청이 정상적으로 처리되지 않는 문제**가 있었습니다.

### 원인 분석

애플리케이션에서 강의를 조회한 뒤 정원을 확인하고 엔티티 값을 변경하는 과정이 여러 단계로 분리되어 있었습니다.

동일한 강의에 요청이 집중될 경우 여러 트랜잭션이 동일한 데이터에 접근하면서 락 경쟁이 발생할 수 있는 구조였습니다.

따라서 애플리케이션에서 조회와 수정을 분리하여 처리하는 대신, **데이터베이스에서 정원 확인과 신청 인원 증가를 하나의 연산으로 처리하는 방식**으로 개선했습니다.

### 개선 방법

강의를 조회한 후 신청 인원을 수정하는 구조를 제거하고 다음과 같은 조건부 UPDATE를 적용했습니다.

```sql
UPDATE classes
SET class_curr_apps = class_curr_apps + 1
WHERE class_seq = ?
  AND class_curr_apps < class_max_cap;
```

조건절에서 현재 신청 인원과 최대 정원을 확인하고 조건을 만족하는 경우에만 신청 인원을 증가시키도록 구성했습니다.

쿼리 실행 결과에 따라 다음과 같이 처리합니다.

```text
UPDATE 결과 = 1
    → 정원 확보 성공
    → 수강 신청 정보 저장

UPDATE 결과 = 0
    → 정원 초과
    → 신청 실패 처리
```

이를 통해 **정원 확인과 신청 인원 증가를 데이터베이스의 단일 원자적 연산으로 처리**할 수 있도록 개선했습니다.

또한 수강 신청 정보 저장까지 하나의 트랜잭션으로 처리하여 저장 과정에서 예외가 발생할 경우 신청 인원 증가 역시 롤백되도록 구성했습니다.

### 중복 신청 방지

동시에 동일한 사용자가 같은 강의에 여러 번 신청하는 경우 애플리케이션 수준의 사전 조회만으로는 중복 요청을 완전히 차단하기 어렵습니다.

따라서 `Enrollment` 테이블에 다음과 같은 복합 UNIQUE 제약조건을 적용했습니다.

```sql
UNIQUE (user_seq, class_seq)
```

이를 통해 동시 요청 상황에서도 동일한 사용자와 강의 조합이 중복 저장되지 않도록 데이터베이스 수준에서 보장했습니다.

### 개선 결과

* 조회 후 엔티티 수정 구조 제거
* 정원 확인과 신청 인원 증가를 하나의 원자적 연산으로 처리
* 동일 강의에 대한 동시 요청 과정에서 발생한 데드락 해결
* 강의 정원을 초과하는 신청 방지
* 동일 사용자의 중복 신청 방지
* 신청 인원과 실제 수강 신청 데이터 간 정합성 유지

## 📨 비동기 처리

수강 신청 요청과 실제 처리 로직을 분리하기 위해 Kafka Producer/Consumer 구조를 적용했습니다.

* Kafka Producer를 통한 수강 신청 요청 발행
* Consumer Group 기반 비동기 요청 처리
* Topic Partition 3개 구성
* Consumer Concurrency 3개 구성

Kafka는 요청을 비동기로 전달하는 역할을 담당하며, **동시 요청에 대한 정원 및 데이터 정합성은 데이터베이스의 조건부 UPDATE와 UNIQUE 제약조건을 통해 보장**하도록 역할을 분리했습니다.
